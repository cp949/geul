# PIT-0025 사본 탐지에 축을 더하기 전에 추적 소스 전량을 새 토큰으로 다시 센다

- 상태: `ACTIVE`
- 적용 영역: test·계약
- 최초 근거: Issue #108

## 상황과 징후

이 저장소는 제품 판단 목록(workspace 루트, glob, headless 패키지)을 한 모듈이 단독 소유하게 하고, 그 사본이 두 번째 파일에 생기는 것을 계약 테스트로 막는다. 판정은 `tokensInOneArrayLiteral()` — 하나의 배열 리터럴 안에 판정 토큰이 임계값 이상 모이면 사본으로 본다.

새 목록을 단독 소유로 옮기면서 축을 하나 더하면, 그 축이 **판정 대상이 아닌 자리**에서 먼저 발화한다. 세 형태가 나온다.

- **계약 테스트 자신의 기대값 배열.** headless 축(`packages/io`·`packages/model`)을 더하자 같은 파일의 열거 결과 6개를 `toEqual([...6개 이름])`으로 단언하던 배열에 두 토큰이 함께 들어 있어 사본으로 잡혔다. 그 배열은 headless 목록의 사본이 아니라 열거 전량의 기대값이다.
- **다른 테스트의 `it.each` 대상 목록.** `tests/workspace-boundaries.test.ts`의 DOM 금지 fixture 대상 `it.each(["packages/model", "packages/io"])`가 잡혔다. 이쪽은 **진짜 사본**이었다 — 같은 제품 판단을 두 번째로 적은 자리다.
- **한국어 산문 주석.** 축을 설명하는 주석이 토큰 목록을 배열 리터럴 문법(`[`·`,`·`]`)으로 그대로 인용하면 그 주석 자신이 걸린다. 이 저장소의 주석 문체가 식별자와 값을 원문 그대로 인용하는 형태라 특히 잘 걸린다.

## 근본 원인

판정이 **의미가 아니라 표기**를 본다. "이 토큰들이 한 배열 리터럴에 모였는가"는 목록의 사본과 그 목록을 부분집합으로 포함하는 더 큰 목록을 구별하지 못한다. 토큰 수가 적을수록(headless 축은 2종) 우연한 동시 등장 확률이 커진다.

이 성질 자체는 의도된 것이다 — 갈린 사본(원소 하나가 빠진 목록)을 잡으려고 부분 일치를 쓴다. 문제는 축을 더하는 사람이 **기존 코드 전량을 그 새 토큰으로 다시 스캔하지 않고** 원본 모듈 하나만 걸릴 것으로 기대한다는 것이다.

## 예방 규칙

- **축을 더하기 전에 추적 소스 전량을 새 토큰으로 먼저 센다.** 걸리는 파일 목록을 손에 쥔 채 각각이 진짜 사본인지 우연한 동시 등장인지 판정한다. 진짜 사본은 없애고(원본을 import해 스프레드로 펼친다), 우연한 동시 등장은 아래 규칙으로 표기를 바꾼다.
- **우연한 동시 등장은 길이 가드 + `toContain()` 반복으로 푼다.** 판정 강도는 `toEqual(정렬된 배열)`과 같다 — 길이 N + 서로 다른 N개의 필수 원소면 집합이 정확히 고정된다.
- **배열 리터럴을 물리적으로 쪼개 피하지 않는다.** `["a"].concat(["b"])`는 임계값 2를 그대로 피한다(실측 점수 1). 그 표기를 저장소에 남기면 진짜 사본을 만들 사람에게 작동하는 회피 예시를 주는 셈이다.
- **주석에 토큰 목록을 배열 리터럴 문법으로 인용하지 않는다.** 가운뎃점(`·`)으로 잇거나 각 토큰을 따로 인용한다.
- **픽스처의 항목이 2개 이상인 자리는 실제 이름 대신 가상 이름(`alpha`·`beta`)을 쓴다.** 실제 값을 쓰면 픽스처 자신이 사본 판정에 걸린다.

## 검증 방법

축을 더하기 전에 후보를 세는 일회용 스캔이다. 저장소 트리에 파일을 남기지 않는다([`PIT-0024`](./PIT-0024-keep-scratch-scripts-out-of-the-repo-tree.md)).

```bash
node -e '
const { execFileSync } = require("node:child_process");
const { readFileSync } = require("node:fs");
const tokens = ["packages/io", "packages/model"];   // 더하려는 축의 토큰
const span = /\[[^[\]]*\]/g;
const hit = (s, t) => new RegExp(`["\x27\`]${t.replace(/[.*+?^${}()|[\]\\]/g, "\\$&")}["\x27\`]`).test(s);
for (const p of execFileSync("git", ["ls-files"], { encoding: "utf8" }).split("\n").filter((p) => /\.(?:m|c)?[jt]sx?$/.test(p))) {
  const src = readFileSync(p, "utf8");
  const n = [...src.matchAll(span)].reduce((b, [s]) => Math.max(b, tokens.filter((t) => hit(s, t)).length), 0);
  if (n >= 2) console.log(n, p);
}'
```

기대는 원본 모듈 1건이다. 그 밖의 파일이 나오면 전부 위 예방 규칙으로 판정하고 처리한 뒤 축을 더한다.

## 알려진 한계

`arrayLiteralSpan`이 중첩 없는 대괄호 스팬만 잡으므로, 배열 안에 다른 대괄호가 하나라도 있으면(인덱스 접근, 중첩 배열, 주석 속 대괄호) 점수가 0이 된다. 객체 값·`.split()`·변수 경유도 0점이다(실측 7종). 임계값을 1로 낮춰도 잡히지 않는다 — 스팬 자체가 사라지기 때문이다. 이 계약은 **사본이 늘어나는 흔한 방향을 막는 장치이지, 저장소에 사본이 없음을 증명하는 장치가 아니다.**
