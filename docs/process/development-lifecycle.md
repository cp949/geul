# 개발 문서 생명주기

## 1. 목적

작업 상태는 GitHub Issues에서 관리하고, 장기간 유지할 계약과 증거만 저장소 문서에 남긴다.

```text
GitHub Issue
→ 계약 확인 또는 spec 승인
→ Issue에 실행 계획·완료 기준 확정
→ 구현과 RED/GREEN
→ 리뷰·수정
→ 단계 완료 판정
→ 제품 문서 동기화
→ Issue 종료
```

이 문서는 문서별 생성·갱신 시점과 작업 종료 조건을 정한다. 에이전트 공통 실행 규칙은 `AGENTS.md`, 이슈 조작 방법은 `docs/agents/issue-tracker.md`가 소유한다.

## 2. 원본의 책임

| 질문 | 단일 기준 |
| --- | --- |
| 지금 어느 단계이며 다음 작업은 무엇인가? | `docs/product/current-status.md` |
| 제품 범위와 기능 상태는 무엇인가? | `docs/product/blocknote-free-feature-inventory.md` |
| 어느 릴리스에서 어떤 조건으로 완료하는가? | `docs/product/roadmap.md` |
| 승인된 기능·기술 계약은 무엇인가? | `docs/specs/` |
| 장기 결정을 왜 선택했는가? | `docs/adr/` |
| 실행 계획과 현재 진행 상태는 무엇인가? | GitHub Issues |
| 반복 실패를 어떻게 예방하고 검증하는가? | `docs/pitfalls/` |
| 단계 완료 기준을 실제로 충족했는가? | `docs/reviews/` |
| 프로젝트 고유 용어는 무엇인가? | `CONTEXT.md` |

한 문서가 다른 문서의 책임을 작업 편의를 위해 복제하지 않는다. 링크로 연결하고 원본만 갱신한다.

## 3. 작업 접수와 범위 확정

1. `docs/product/current-status.md`와 관련 GitHub Issue를 읽는다.
2. `CONTEXT.md`, inventory, roadmap, 관련 spec·ADR·pitfall을 확인한다.
3. 대상 코드와 기존 테스트로 현재 구현 사실을 확인한다.
4. 목표, 포함·제외 범위, 구현 순서, 완료 기준과 검증 명령을 이슈 초안으로 기록한다.
5. 제품 범위나 공개 계약이 불명확하면 구현 전에 사용자 결정을 받는다.

GitHub 쓰기는 사용자 지시를 기다린다. 등록 전 이슈와 댓글은 `_works/<작업 폴더>/pending-issues/`에 초안으로 남긴다. 계약은 `docs/agents/issue-tracker.md`의 "게시 승인"이 소유한다.

이슈 생성만으로 제품 범위가 승인되지는 않는다. inventory, roadmap 또는 승인된 spec에 없는 작업은 승인 전 현재 구현 범위에 포함하지 않는다.

특정 worktree, branch, commit 범위, handoff, Issue 또는 spec을 지정받으면 그것을 실행 계약으로 취급한다.

## 4. 설계 문서와 ADR

새 제품 결과, 공개 API, 저장 계약, 보안 경계 또는 여러 모듈이 공유할 기술 계약을 정하면 구현 전에 `docs/specs/`에 기록하고 사용자 승인을 받는다.

ADR은 다음 세 조건을 모두 만족할 때만 작성한다.

1. 결정을 되돌리는 비용이 크다.
2. 배경이 없으면 미래 작업자가 의도된 선택임을 알기 어렵다.
3. 실제 대안 사이의 trade-off를 거쳐 선택했다.

spec은 제공할 계약을, ADR은 장기 선택과 이유를 소유한다. 실행 순서와 진행 기록은 GitHub Issue에만 둔다.

프로젝트 고유 용어가 확정되면 `CONTEXT.md`에 한두 문장 정의와 `_Avoid_` 표현을 기록한다. 코드 식별자나 일반 프로그래밍 용어를 복제하지 않는다.

## 5. 구현과 검증

1. 시작 시 branch, worktree와 `git status --short`를 확인한다. 구현은 `dev`에서 분기한 작업 브랜치에서 한다 — 수명은 `AGENTS.md`의 "작업 브랜치 수명"이 소유한다.
2. 기존 modified, untracked와 ignored 파일을 사용자 작업으로 간주해 보존한다.
3. 기능 또는 버그 수정은 회귀 테스트를 추가하고 RED를 확인한다.
4. 최소 구현으로 GREEN을 만든 뒤 변경 범위의 품질을 정리한다.
5. focused 검증을 실행하고 실패를 baseline과 현재 변경으로 구분한다.
6. 실행 결과와 남은 제한을 이슈 체크리스트 갱신 초안으로 기록한다.

현재 범위 밖 결함이나 개선은 별도 이슈 초안으로 만든다. 초안에는 발견 위치, 영향, 현재 범위에서 제외한 이유와 완료 조건을 기록하고 현재 변경에 섞지 않는다.

다른 단계에서도 같은 원인으로 재발할 수 있고 구체적인 예방·검증 규칙을 만들 수 있으면 `docs/pitfalls/`에 상세 문서를 추가하거나 갱신하고 INDEX를 같은 변경에서 동기화한다.

## 6. 리뷰와 수정

리뷰는 다음 입력을 함께 확인한다.

- 관련 GitHub Issue의 범위와 완료 기준
- 승인된 spec과 roadmap 완료 조건
- 관련 ADR과 `ACTIVE` pitfall
- 실제 코드, 테스트와 변경 diff

결함 심각도는 다음과 같다.

- `BLOCKER`: 안전, 데이터 또는 핵심 계약을 깨뜨려 결과물을 사용할 수 없다.
- `MAJOR`: 승인된 필수 요구사항이나 회귀 계약을 충족하지 않는다.
- `MINOR`: 필수 계약을 깨뜨리지는 않지만 품질 또는 유지보수 개선이 필요하다.

`BLOCKER`와 `MAJOR`는 수정하고 같은 범위를 다시 검증·리뷰한다. 현재 범위에서 수정하지 않는 `MINOR`는 필수 완료 기준을 위반하지 않는 근거와 함께 별도 이슈 초안으로 분리한다.

## 7. 단계 완료 판정

`docs/reviews/<phase>-completion.md`는 단계별 고정 완료 기준과 판정 회차를 분리한다. 작업 중간 로그는 기록하지 않고 최종 판정에 필요한 재현 가능한 증거만 남긴다.

각 항목은 다음 중 하나로 판정한다.

- `PASS`: 현재 결과물과 재현 가능한 증거가 기준을 충족한다.
- `FAIL`: 기준 불충족이나 회귀가 확인됐다.
- `BLOCKED`: 필요한 결정, 환경 또는 외부 조건이 없어 판정할 수 없다.
- `NOT_RUN`: 필요한 검증을 아직 실행하지 않았다.

각 회차에는 회차 ID, 판정 시점, 대상 commit 또는 작업공간 상태, 항목별 상태와 근거, 발견 결함, 실행 명령과 결과, 다음 행동을 기록한다. 이전 회차를 덮어쓰지 않는다.

다음 조건을 모두 만족할 때만 단계를 완료한다.

- 모든 필수 항목의 최신 판정이 `PASS`다.
- 열린 `BLOCKER` 또는 `MAJOR`가 없다.
- 현재 결과물에서 최종 검증이 통과했다.
- inventory, roadmap, current-status와 관련 문서가 실제 상태와 일치한다.
- 현재 범위 밖 남은 작업이 별도 이슈 초안으로 기록됐다.
- 새로 확인한 재발 가능 위험이 pitfall에 반영됐다.

승인된 완료 기준을 판정 과정에서 삭제하거나 약화하지 않는다. 기준 변경이 필요하면 사용자 승인을 받고 완료 문서의 계약 변경 이력에 이전 기준, 변경 이유와 영향 범위를 남긴다.

## 8. 문서 갱신표

| 발견 또는 변경 | 갱신 대상 | 승인 경계 |
| --- | --- | --- |
| 프로젝트 고유 용어 확정 | `CONTEXT.md` | 관련 계약 변경 시 사용자 보고 |
| 승인된 기능·기술 계약 | `docs/specs/` | 구현 전 사용자 승인 |
| 장기 아키텍처 선택 | `docs/adr/` | 결정 승인 후 `accepted` |
| 현재 범위 밖 작업 발견 | `_works/<작업 폴더>/pending-issues/` 초안 | 등록과 현재 범위 편입 모두 사용자 지시 필요 |
| 재발 가능한 함정 확인 | `docs/pitfalls/` 상세 + INDEX | 예방 규칙을 이후 Issue·리뷰에 적용 |
| 완료 기준 변경 | 관련 `docs/reviews/` 문서 | 사용자 승인 필요 |
| 단계 검증 종료 | 관련 `docs/reviews/` 문서 | 증거에 따라 판정 |
| 제품 기능 상태 변경 | inventory와 roadmap | 같은 변경에서 동기화 |
| 현재 단계 또는 다음 작업 변경 | current-status | 실제 상태와 동기화 |

## 9. 충돌 처리

문서가 충돌하면 먼저 각 문서의 책임 범위를 확인한다. 코드와 테스트는 현재 구현 사실을 판정하는 근거지만 제품 범위나 공개 계약을 자동으로 변경하지 않는다.

한 문서가 자기 책임 범위에서 다른 문서와 충돌하면 임의로 선택하거나 조용히 덮어쓰지 않는다. 확인된 사실, 충돌하는 계약, 영향 범위와 사용자 결정이 필요한 지점을 구분해 보고한다.

## 10. 작업 종료

1. focused 검증과 범위에 맞는 최종 게이트를 실행한다.
2. `git diff --check`와 `git status --short`를 확인한다.
3. 단계 또는 릴리스 검증이면 관련 completion 문서를 갱신한다.
4. 별도 Issue와 pitfall의 생성·상태 변경 여부를 확인한다.
5. 제품 문서와 실제 상태가 일치하는지 확인한다.
6. Issue에 검증 결과, 남은 제한과 다음 행동을 기록한다.
7. 완료 기준을 충족한 Issue만 종료한다.

commit, merge, push, tag와 PR은 각각 별도 요청이 필요하다.
