# workflow-shared

`qq-workflow`와 `roadmap-workflow`가 공유하는 실행 계약이다. 두 흐름의 계획·구현·리뷰 절차와 산출물 구성은 각 흐름 문서가 소유하고, 여기서는 두 흐름이 동일하게 쓰는 기계적 계약만 다룬다 — DELTA 크기 규칙, 재그룹화 실행 명령, 커밋 해시 참조, 브랜치 수명, pending 3종, subagent 협업 규칙, 리뷰 산출물 형식.

이 문서는 독립 레인이 아니다. 레인 선택은 [`../../AGENTS.md`](../../AGENTS.md)의 "레인 선택 규칙"이 소유한다.

## DELTA 크기 규칙

qq-workflow가 작업 적합성을 판정하고, roadmap-workflow가 RD 내 DELTA 하나의 크기를 판정할 때 이 기준을 쓴다. 기준은 리뷰어가 DELTA 하나를 판정하는 동안 컨텍스트가 가득 차지 않는 것이다 — 리뷰어가 담아야 하는 것은 `계획 문서 + 변경 diff + 변경 파일 전문 + 직접 의존 파일`이다.

선호값 — 이 크기 이하에 들어오는 독립 완료 조건과 의존 경계를 우선 찾는다.

- 변경 diff 700줄(추가 + 삭제)

700줄을 넘겨도 같은 계약과 RED/GREEN 단위를 인위적으로 끊지 않는다면 하나로 유지할 수 있다. 이때도 아래 상한은 지킨다.

상한 — 하나라도 넘으면 이 크기에 맞지 않는다.

- 변경 diff 3,000줄(추가 + 삭제)
- 신규·수정 소스 파일 6개
- 리뷰어가 전문을 읽어야 하는 파일 합계 2,000줄

하한 — 만족하지 못하면 앞뒤 작업 단위에 합친다.

- 완료 조건이 1개 이상이고, 그것을 RED로 만들 변이를 적을 수 있다.

경계 신호 — 상한 안이어도 나누는 편이 낫다.

- 완료 조건 한 문장에 "그리고"가 두 번 이상 나온다.
- 서로 무관한 공개 계약 두 개를 동시에 바꾼다.
- 서로 다른 패키지 세 개 이상을 건드린다.

상한을 넘거나 경계 신호가 나타났을 때 무엇을 하는지는 호출 문서가 정한다 — qq-workflow는 "단계-2. 구현"이 정지·보고를, roadmap-workflow는 "승격 예외"가 qq-workflow 승격을 정한다.

**실측 보정.** 위 수치는 첫 기준선이다. 리뷰 subagent가 파일을 다 읽지 못했다고 보고하거나 컨텍스트 압박으로 판정을 유보하면 이 기준이 너무 느슨했다는 신호다. 정상 분할 지식은 `pending-guides/`에, 가이드를 따르지 않았거나 모호하게 해석해 반복된 실수는 `pending-pitfalls/`에 남긴다.

## 재그룹화 실행 명령

이 절이 실행 명령, 그룹 순서와 무결성 판정을 함께 소유한다.

### 전제

다음이 어긋나면 아무것도 바꾸지 않고 정지한다.

- `git status --short`가 비어 있어야 한다.
- 작업 브랜치가 존재하고 `git log --oneline dev..<브랜치>`가 비어 있지 않아야 한다.
- 이전 실행이 남긴 `-tip` ref가 없어야 한다. `git for-each-ref refs/backup/<브랜치>-tip`이 빈 출력이어야 한다.

더러운 작업 트리에서 재조립을 시작하면 미커밋 변경이 그룹 커밋에 조용히 접혀 4단계의 트리 diff가 비지 않는다. 그 상태로 "되돌리고 2단계부터 다시 한다"를 반복해도 원인이 트리 오염이면 끝나지 않는다 — 재조립을 시작하기 전에 이 전제부터 확인한다.

`-tip`이 남아 있으면 더 조용히 깨진다. 5단계를 건너뛰어도 6단계의 `git branch -f`가 실패하지 않고 **이전 실행의 커밋**을 브랜치에 박는다. 그 트리는 `-pre-squash`와 같으므로 6단계 재대조가 빈 출력으로 통과하고 `git merge --ff-only`도 성공한다 — 이번 실행의 그룹 분할과 커밋 메시지만 사라지고 아무 게이트도 울리지 않는다. `-tip`이 남아 있다는 것은 이전 실행이 6단계나 7단계에서 끝나지 않았다는 뜻이다. 그 실행을 먼저 정리한다.

### 절차

1. 백업 ref를 남긴다. 백업 없이 재조립하지 않는다.

   ```bash
   git update-ref refs/backup/<브랜치>-pre-squash HEAD
   ```

2. 그룹을 정한다. `git log --oneline --name-only dev..HEAD`로 같은 파일·같은 줄을 왕복하는 상쇄 쌍을 먼저 찾는다. revert·되돌림 성격의 커밋은 원인 커밋과 같은 그룹에, 원인 커밋 뒤에 둔다.
3. `dev`에서 분리해 그룹별로 재조립한다. 커밋을 원래 순서대로 나열하고 그룹마다 한 번 커밋한다.

   ```bash
   git switch --detach dev
   git cherry-pick -n <그룹1 커밋...>
   git commit -m "<그룹1 메시지>"
   git cherry-pick -n <그룹2 커밋...>
   git commit -m "<그룹2 메시지>"
   ```

   커밋 메시지는 한글로 쓰고 `Co-Authored-By`와 생성 표시 라인을 넣지 않는다.

   `git commit`이 `커밋할 사항 없음`으로 실패하면 그 그룹은 내부에서 전부 상쇄된 것이다. 에러가 아니므로 그룹을 버리고 다음으로 넘어가되, 커밋을 의도적으로 버렸다는 사실을 보고에 적는다.

   `git cherry-pick`이 충돌로 멈추면 `git cherry-pick --continue`를 쓰지 않는다. `-n`이 남긴 스테이지 변경 때문에 `로컬 변경 사항을 cherry-pick 때문에 덮어 쓰게 됩니다`로 실패한다(exit `128`). 해결 경로는 다음이다.

   ```bash
   # 충돌 해결 후
   git add <파일>
   git cherry-pick --quit          # 시퀀서 상태만 정리한다. 작업 트리는 그대로 남는다
   git cherry-pick -n <남은 커밋>  # 나머지를 이어서 pick
   ```

4. 트리를 대조한다. 3단계에서 의도적으로 버린 그룹이 없다면 빈 출력이어야 한다. 버린 그룹이 없는데도 비어 있지 않으면 그룹 순서가 잘못된 것이다. 되돌리고 2단계부터 다시 한다.

   ```bash
   git diff refs/backup/<브랜치>-pre-squash HEAD --stat
   ```

5. 그룹 경계마다 typecheck가 통과하는지 확인한다. 검증을 시작하기 전에 재조립 tip을 ref로 고정한다 — 이 단계가 HEAD를 중간 그룹 커밋으로 옮기므로, 고정해 두지 않으면 6단계가 그 HEAD를 브랜치에 박아 뒤 그룹을 조용히 버린다.

   ```bash
   git update-ref refs/backup/<브랜치>-tip HEAD   # 재조립 tip 고정. 검증 전에 한다
   git switch --detach <그룹 커밋>                # 그룹마다 반복
   # 해당 범위의 focused 검증을 실행한다
   ```

   역순으로 검증하거나 일부만 검증하거나 중간에 멈춰도 tip은 ref에 남는다.

6. 작업 브랜치를 재조립 tip으로 옮기고 `dev`로 이전한다. `HEAD`를 대상으로 쓰지 않는다 — 5단계가 HEAD를 중간 그룹 커밋에 남겨 뒀으면 뒤 그룹이 사라지고, 그래도 `merge --ff-only`는 fast-forward라 성공한다.

   ```bash
   git branch -f <브랜치> refs/backup/<브랜치>-tip
   git switch <브랜치>
   git diff refs/backup/<브랜치>-pre-squash <브랜치> --stat   # 병합 직전 재대조. 4단계와 같은 기대치다
   git switch dev
   git merge --ff-only <브랜치>
   ```

   재대조가 4단계와 같은 결과가 아니면 병합하지 않는다. 5단계가 HEAD를 옮긴 뒤 브랜치가 tip이 아닌 커밋을 가리키게 됐다는 뜻이다.

   ff가 거절되면 재조립 중 `dev`가 움직인 것이다. 3단계를 현재 `dev` 기준으로 다시 실행한다.

7. `git branch -d <브랜치>`로 삭제하고 ref를 정리한다. 백업 ref는 6단계의 재대조와 병합이 끝난 뒤에만 지운다.

   ```bash
   git update-ref -d refs/backup/<브랜치>-tip
   git update-ref -d refs/backup/<브랜치>-pre-squash
   ```

### 금지

- `git rebase -i`. 에이전트 세션은 `GIT_EDITOR=true`라 아무것도 합치지 않은 채 `Successfully rebased`와 exit code `0`을 낸다 — [`PIT-0023`](../pitfalls/PIT-0023-editor-opening-git-commands-succeed-silently.md). `GIT_SEQUENCE_EDITOR` 우회도 쓰지 않는다.
- 명령의 성공 문구를 결과 판정 근거로 쓰기. 판정은 4단계와 6단계의 트리 diff로만 한다. `merge --ff-only`의 성공은 뒤 그룹이 사라져도 나온다.
- push, tag, PR 생성. `dev` push는 사용자가 별도로 지시한다.
- `main`을 대상으로 하는 merge, rebase, push.
- `git reset --hard`, 강제 push, 광범위한 `git clean`.

## 커밋 해시 참조

해시는 작업 브랜치가 `dev`로 이전되는 순간에만 불변이 된다. 이전 전에는 이슈, 댓글, 초안과 어느 산출물에도 해시를 쓰지 않는다. 참조는 작업 브랜치명, 파일 경로와 줄 번호, 테스트 제목, 검증 명령 출력으로 한다. 이전 후 확정된 해시는 `dev`의 커밋 로그가 기록한다 — 별도 산출물이나 `_meta.md`에 다시 적지 않는다.

## 브랜치 수명

작업 브랜치는 작업당 하나이고 여러 개가 동시에 존재할 수 있다. 각각 `dev`에서 분기한다. worktree는 만들지 않는다. 앞 작업의 산출물이 필요한 의존 작업일 때만 그 브랜치에서 분기하고 의존을 실행 ledger(`progress.md`)에 적는다.

작업 브랜치는 push하지 않는다. push 대상은 `dev`뿐이고 명시적 지시를 기다린다.

## pending-issues, pending-guides와 pending-pitfalls

셋 다 **작업의 어느 지점에서든 언제라도 추가할 수 있다.** 현재 범위 밖에서 발견한 것을 현재 변경에 섞지 않기 위한 자리다.

**예외 — 이전 전 hash.** 작업 branch commit hash가 이전 전 산출물에 남은 경우 현재 범위와 무관하게 즉시 수정한다. pending 항목으로 미루지 않는다. 위 "커밋 해시 참조" 절이 원본이다. 위반을 서술할 때도 hash 값은 인용하지 않고 수정 산출물을 포함해 다시 검사한다.

`pending-issues/NN.md` — 등록 전 이슈·댓글 초안. 발견 위치, 영향, 현재 범위에서 제외한 이유, 완료 조건을 적는다. 파일 형식, 등록 기준과 게시 승인은 [`./issue-tracker.md`](./issue-tracker.md)가 소유한다 — 초안은 그 문서의 "초안 형식"을 그대로 따른다.

`pending-guides/NN.md` — 신규 가이드 또는 기존 가이드 수정·보강 초안. 적용 조건 / 구현 규칙 / 완료 기준 / 관련 기존 helper를 적는다. 기존 가이드 보강이면 대상 `G-<카테고리>-<번호>`와 모호했던 문구를 함께 적는다.

`pending-pitfalls/NN.md` — 가이드나 명시적 계약을 따르지 않았거나 모호하게 해석해 반복된 실수. 적용 조건 / 오해하기 쉬운 신호 / 원인 / 탐지를 적는다. 발견한 정상 회피 경로는 `pending-guides/` 초안에 적는다. 승격 기준은 [`../pitfalls/INDEX.md`](../pitfalls/INDEX.md)의 "승격 기준"이 소유한다.

## subagent 협업 규칙

메인 세션은 조율자이고 조사·구현·리뷰는 subagent가 한다. 어느 단계가 이 모드를 쓰는지는 호출 문서(qq-workflow, roadmap-workflow)가 정한다.

쓰는 이유는 둘이다. 조사와 리뷰를 여러 시선으로 나눠 파일 단위 시야에 갇히는 것을 줄인다. 메인 세션의 컨텍스트를 조율과 판단에 남긴다.

- subagent는 이 세션의 맥락을 물려받지 않는다. 프롬프트에 대상 이슈 번호, 작업 브랜치명, 작업 폴더 경로, 읽어야 할 문서 경로, 편집 허용 범위와 반환 형식을 모두 적는다.
- subagent에 worktree 격리를 주지 않는다. 작업 트리 하나를 공유하므로 **파일을 쓰는 subagent는 한 번에 하나만 띄운다.** 병렬 dispatch는 읽기 전용 조사·리뷰에만 쓴다.
- 커밋은 메인 세션이 한다. subagent 작업 하나가 끝날 때마다 diff를 확인하고 커밋한다. 커밋 단위와 메시지는 재그룹화 대상이라 한 곳에서 정한다.
- 정지 조건은 subagent에도 그대로 적용된다. push, GitHub 쓰기, `dev` 병합과 재그룹화 금지를 프롬프트에 명시한다.
- subagent 보고는 근거와 함께 받는다 — 파일 경로와 줄 번호, 테스트 제목, 실행한 명령과 출력. 근거 없는 "고쳤다"는 받아들이지 않고 메인 세션이 직접 확인한다.
- 사용자 결정이 필요한 지점은 subagent가 추측하지 않고 그대로 올린다. 사용자에게 묻는 것은 메인 세션이다.

## 리뷰 산출물 형식

`IMPL-REVIEW-NN.md`는 append-only 시퀀스다. 이전 회차를 덮어쓰지 않는다. 여러 단계가 같은 시퀀스에 이어 쓰는 경우 파일 머리말이 어느 단계의 어떤 초점인지 밝힌다.

형식 — 네 절만 가진다.

```markdown
# IMPL-REVIEW-01

- <호출 문서가 정한 식별 필드>: <값>
- 초점: <초점>
- 대상: <작업 브랜치> / <범위>
- 시점: yyyy-MM-dd

## 발견 <!-- 확정 결함만 기록한다 -->

### F1 <제목> — MAJOR

- 위치: <파일:줄>
- 재현: <명령 또는 조건>
- 실제/기대: <실측>
- 위반 계약: <문서 경로와 문구>

## 처리 <!-- 발견별 수정 / 범위 밖 / 오탐과 변경한 테스트·코드 -->

## 검증 <!-- 최종 focused gate와 결과 -->

## 남은 위험 <!-- 현재 변경으로 닫히지 않은 위험만 -->
```

기록하지 않는 것: 어느 reviewer가 같은 결함을 몇 번 발견했는지, 조사 중 확인한 모든 정상 경로, 테스트 전체 출력, commit message와 중복되는 변경 설명.

`## 남은 위험`을 비워두지 않는다. 없다고 판단했으면 어디를 확인해서 그렇게 판단했는지 적는다.

심각도는 [`../process/development-lifecycle.md`](../process/development-lifecycle.md)의 `BLOCKER` / `MAJOR` / `MINOR`를 그대로 쓴다. **`BLOCKER`·`MAJOR`는 위반한 필수 요구사항·회귀 계약의 문서 경로와 문구를 인용할 때만 부여한다.** 명시 계약 없이 품질 저하만 확인했으면 `MINOR`로 판정하거나 계약 공백으로 보고한다. `BLOCKER`와 `MAJOR`는 수정하고 같은 범위를 다시 검증한다. 수정하지 않는 `MINOR`는 근거와 함께 `pending-issues/`로 분리한다. 분리 대상은 [`./issue-tracker.md`](./issue-tracker.md)의 "등록 기준"을 통과하는 것뿐이다.
