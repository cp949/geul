# ff-workflow

계획을 튼튼하게 해서 구현을 혼란 없이 빠르게 하고, 리뷰를 튼튼하게 해서 구현 실수를 보완하는 다단계 작업 흐름이다. 트랙 9개와 작업 브랜치, `_works/` 작업공간을 쓴다. 슬래시 커맨드는 없다 — 이 문서 하나가 절차를 소유하고 사용자가 트랙을 지시한다.

이 흐름은 세 가지에 기댄다.

1. 계획을 **DELTA 단위로 분할**하고, 그 분할 자체를 별도 트랙에서 리뷰한다(트랙-2). 구현이 시작된 뒤 드러나는 계획 결함이 가장 비싸다.
2. 구현 후 리뷰를 **누락 탐지**(트랙-5)와 **결함 탐지**(트랙-6) 두 렌즈로 나눈다. 계획을 들고 보는 눈은 계획의 사각지대를 그대로 물려받는다.
3. 절차를 문서 하나가 소유한다. 슬래시 커맨드나 트랙별 파일로 쪼개면 공통 계약(작업 폴더, 브랜치 수명, 정지 조건)을 여러 곳에서 동기화해야 한다. interactive Git의 환경 함정만 [`PIT-0023`](../pitfalls/PIT-0023-editor-opening-git-commands-succeed-silently.md)이 별도로 소유한다.

## 언제 쓰나

진입 규칙은 [`../../AGENTS.md`](../../AGENTS.md)의 "레인 선택 규칙"이 소유한다. 이 흐름으로 들어오는 경로는 둘이다 — 사용자가 `ff-workflow`를 지목했거나, 레인 명시 없는 이슈 작업에서 자동 선택이 ff를 골랐다. 그 외에는 기본값이 아니다 — 지시가 없으면 "기본 레인"으로 진행한다.

기본값이 아닌 이유는 비용이다. 트랙 9개와 리뷰 3회는 파일 단위 시야로는 볼 수 없는 결함을 잡으려고 치르는 값이다. 공용 test support의 교차 파일 검토는 [`G-TST-002`](../guides/G-TST-002-own-shared-test-support.md)가 그 형태를 설명한다. 간단한 작업의 경량 흐름은 [`./qq-workflow.md`](./qq-workflow.md)가 따로 있다.

에이전트는 기본 레인이나 qq-workflow로 시작한 작업을 스스로 ff-workflow로 승격하지 않는다. 작업이 예상보다 커졌으면 그 사실을 완료 보고의 "남은 제한, 위험"에 적고 판단은 사용자에게 남긴다.

트랙 지시는 작업 폴더를 항상 함께 받는다.

```
ff-workflow의 트랙-4의 DELTA-01을 진행 (계획서: _works/20260823-01-작업제목)
ff-workflow의 트랙-4의 모든 DELTA를 진행 (계획서: _works/20260823-01-작업제목)
```

작업 폴더 인자는 접두 매칭을 허용한다. `20260823-01`처럼 앞부분만 주어도 `_works/` 아래에서 유일하게 매칭되면 그 폴더로 해석한다. `_works/` 접두사는 붙여도 생략해도 된다. 매칭이 없거나 둘 이상이면 후보를 출력하고 정지한다.

용어: 이 흐름은 **트랙**과 **DELTA**만 쓴다.

### 실행 수단 선택

각 트랙은 입력·완료 기준·반환 형식이 포함된 prompt 계약을 제공한다. 트랙이 정한 메인 세션·subagent 역할, 읽기·쓰기 범위와 직렬·병렬 조건은 그대로 유지한다.

## 작업 폴더

```
_works/<yyyyMMdd>-<NN>-<slug>/
  _meta.md
  progress.md
  00-계획-초안.md
  01-계획.md
  DELTA-01.md  DELTA-02.md  DELTA-02a.md  ...
  PLAN-REVIEW-01.md  PLAN-REVIEW-02.md  ...
  02-테스트-계획.md
  03-최종-완료-체크리스트.md
  IMPL-REVIEW-01.md  IMPL-REVIEW-02.md  ...
  04-작업결과.md
  pending-issues/01.md  02.md  ...
  pending-guides/01.md  02.md  ...
  pending-pitfalls/01.md  02.md  ...
```

`NN`은 그날 순번이다. 이슈가 있으면 slug 앞에 `issue<번호>-`를 붙인다(`20260823-01-issue26-editmap-perf`).

### `_meta.md`

서술 문서가 아니라 manifest다. 다음 세 필드만 둔다.

```markdown
---
작업 브랜치: <type>/<이슈번호>-<slug>
대상 이슈: #NN | 없음
상태: 진행중
---
```

트랙-8의 `dev` 이전이 끝나면 `상태: 완료`로 바꾼다. `상태`는 트랙-0이 같은 이슈의 미완료 작업 폴더를 이어받을지 판정하는 데만 쓴다 — 트랙별 완료 판정에는 쓰지 않는다.

여기에 두지 않는 것과 그 소유자:

- 시작일 — 작업 폴더 이름이 소유한다.
- 트랙별 진행 이력 — 트랙별 산출물, 실행 ledger(`progress.md`), Git이 소유한다.
- 판단과 근거(Ruling) — `01-계획.md`의 "## 결정" 절이 소유한다.
- 확정 커밋 해시 — Git과 `docs/history/`가 소유한다.

### `progress.md` — 실행 ledger

작업당 하나인 실행 ledger다. 트랙-4의 상세 실행 증거(등급 판정, agent 호출, 테스트 결과, 남은 위험)를 필수로 담고, 다른 트랙도 산출물이 담지 못하는 실행 메모(작업 폴더 이어받기, 등급 전환 같은 사건)를 여기에 append한다. 형식은 "트랙-4. DELTA 구현"의 ledger 규칙이 소유한다.

### 트랙 진입 판정

**트랙 진입 가부는 선행 산출물 파일의 존재로 판정한다.** 필요한 파일이 없으면 추측해서 진행하지 않고 무엇이 없는지 보고하고 정지한다. `_meta.md`의 `상태`는 이어받기 판정용이지 트랙 게이트가 아니다.

## 트랙 계약

각 트랙 절은 **입력 / 출력 / 절차 / 정지 조건**을 명시한다. 입력 명시가 "앞선 맥락이 없는 에이전트가 폴더만 보고 진행한다"를 실제로 지게 만드는 장치다.

**종료 기록.** 트랙 실행 이력은 각 트랙의 산출물과 실행 ledger(`progress.md`)가 소유한다 — `_meta.md`에 진행 로그를 쓰지 않는다. 사용자 결정과 판단이 필요했던 지점(Ruling)은 `01-계획.md`의 "## 결정"에 append한다 — 주제, 결정, 근거, 틀렸을 때 비용을 적는다. `01-계획.md`가 아직 없는 트랙-0의 결정은 `00-계획-초안.md`에 적고 트랙-1이 "## 결정"으로 옮긴다.

**재실행.** 트랙-2, 3, 4, 5, 6, 7은 이미 완료했어도 사용자가 지시하면 한 번 더 실행한다. 완료했다는 이유로 거절하지 않는다. 재실행의 산출물은 기존 파일을 덮어쓰지 않고 다음 번호로 append하며, 트랙-3처럼 번호 없는 산출물은 갱신하되 앞 판단과 달라진 것이 무엇이고 왜 달라졌는지 그 산출물에 적는다 — 조용히 바꾸지 않는다. 재실행이 게이트를 다시 밟게 하면 그 게이트도 다시 실행한다 — 트랙-5 재실행은 `pnpm verify` 전량을 다시 돌린다.

## 트랙-0. 브레인스토밍과 계획 초안

- 입력: `AGENTS.md`의 "작업 시작 순서" 1~9, 대상 이슈(`gh issue view <번호> --comments`), 사용자 대화
- 출력: 작업 폴더, `_meta.md`, `00-계획-초안.md`, 작업 브랜치
- 절차: 작업 폴더를 먼저 정한다. `_works/`에 같은 이슈를 대상으로 하는 미완료 작업 폴더가 있으면 새로 만들지 않고 이어받는다 — 판정은 `_meta.md`의 `상태`가 `진행중`이면 미완료다. 이어받으면 그 사실을 실행 ledger(`progress.md`)에 적는다. 그다음 아래 "조사·결정 prompt"로 진행한다. 의사결정이 필요한 지점은 추측하지 않고 사용자에게 묻는다. 사전 조사가 여러 갈래로 갈리면 읽기 전용 조사 subagent를 갈래마다 하나씩 병렬로 띄우고 결과를 메인 세션이 합친다. `git switch -c <type>/<이슈번호>-<slug> dev`로 브랜치를 만든다 — 분기 기준을 `dev`로 명시한다. 이슈가 없으면 번호를 생략한다. worktree는 만들지 않는다.
- 정지: 커밋하지 않는다. 브랜치만 만든다.

### 조사·결정 prompt

```text
AGENTS.md의 작업 시작 순서 1~9, 대상 이슈와 사용자 대화를 입력으로 계획 초안을 만든다.

1. 현재 코드·테스트·계약에서 확인한 사실과 아직 확인하지 않은 가정을 구분한다.
2. 목표, 포함·제외 범위, 구현 순서, 완료 기준과 검증 명령을 작성한다.
3. 구현 전에 정해야 하는 선택지만 최대 3개로 압축하고 단일 권장안을 제시한다.
4. 사용자 결정이 필요한 항목은 추측하지 않고 질문한다.
5. 결정된 항목은 주제, 결정, 근거와 틀렸을 때 비용으로 기록한다.

반환: 00-계획-초안.md에 들어갈 내용, 열린 결정, 조사 근거와 남은 불확실성.
```

## 트랙-1. DELTA 분할

- 입력: `00-계획-초안.md`
- 출력: `01-계획.md`, `DELTA-NN.md`
- 절차: `01-계획.md`는 목표, 포함·제외 범위, DELTA 목록과 실행 순서, DELTA 사이 의존, 요구사항 추적표, "## 결정"(트랙-0의 결정을 옮겨 시작)을 담고 각 DELTA 파일을 링크한다. `docs/guides/INDEX.md`에서 각 DELTA의 작업 조건과 맞는 가이드를 선택한다. 각 DELTA는 "DELTA 계약" 절의 형식과 크기 규칙을 따른다.
- 게이트: 요구사항 추적표에 담당 DELTA나 완료 조건이 없는 행이 있으면 트랙-1을 완료하지 않는다.
- 정지: 코드를 고치지 않는다.

**요구사항 추적표.** 조사 사실이 담당 DELTA의 완료 조건으로 전사됐는지를 기계적으로 확인하는 장치다. 트랙-0이 원인을 이미 확인했어도 이 표를 거치지 않으면 DELTA에서 누락된다.

```markdown
## 요구사항 추적

| 원본 요구사항 | 담당 DELTA | 완료 조건 | 관련 계약 |
| --- | --- | --- | --- |
| Issue #NN 완료 기준 1 | DELTA-01 | 조건 1, 2 | spec §N |
```

작성 규칙:

- 이슈의 각 완료 기준을 한 행 이상으로 옮긴다.
- 사용자 결정("## 결정"의 Ruling)과 트랙-0이 확인한 원인 중 구현 성립에 필요한 선행 조건을 옮긴다.
- 관련 spec·ADR의 필수 갱신 여부를 표시한다.

DELTA를 나중에 끼워야 하면 `DELTA-02a.md`, `DELTA-02b.md`로 추가한다. 기존 번호를 다시 매기지 않는다 — 이미 나간 리뷰와 로그의 참조가 깨진다.

## 트랙-2. 계획서 리뷰 및 수정

- 입력: `01-계획.md`(요구사항 추적표 포함), `DELTA-*.md`, 관련 spec·ADR·개발 가이드, 적용 조건이 맞는 `ACTIVE` pitfall, 대상 코드
- 출력: 라운드마다 `PLAN-REVIEW-NN.md`, 수정된 `DELTA-*.md`
- 절차: subagent 협업 모드로 진행한다. 아래 렌즈 셋을 읽기 전용 subagent 3개에 하나씩 병렬 dispatch한다. 기본 경로는 두 라운드다 — 라운드 1이 구조적 발견을 전면 수집하고, 라운드 2가 수정 영향을 clean review한다.
  1. **범위 정합** — DELTA 집합이 이슈·spec이 요구하는 목표를 구조적으로 빠짐없이 담는가. 요구사항 추적표의 각 행이 실제로 담당 DELTA의 완료 조건에 연결되는가. 비목표로 명시한 범위를 벗어나는 DELTA가 있는가.
  2. **분할과 순서** — DELTA 경계가 책임 단위로 맞는가. 선행 관계(의존 순서)가 성립하는가. 어느 DELTA도 담당하지 않는 구조적 틈이 있는가.
  3. **외부 계약과 가이드** — 승인된 spec·ADR, 개발 가이드, 적용 조건이 맞는 `ACTIVE` pitfall, `AGENTS.md`의 아키텍처 불변식과 어긋나는가. 정상 구현 경로가 없는 `guide gap`이 있는가.

  세 렌즈 모두 **구조적 결함만** 본다. 정확한 파일 목록, 구현 절차 서술, 검증 명령 문구, 완료 조건의 수치·건수, 중간 상태 예측은 리뷰 대상이 아니다 — dispatch 프롬프트에 이 제외 범위를 명시한다. 이런 세부는 트랙-4가 실제 코드 상태를 보고 현장에서 보정한다. 각 subagent는 발견뿐 아니라 **검토한 요구사항·계약과 그 증거**를 함께 제출한다 — 라운드 2가 미검토 항목을 대조할 입력이다.

- 라운드 1(발견): 메인 세션이 세 보고를 합쳐 중복을 제거하고, 각 발견에 아래 구조 판정식을 적용한 뒤, 인정한 모든 구조적 `BLOCKER`·`MAJOR`를 한 번에 수정한다. 각 DELTA의 **적용 계약과 가이드**·**적용 함정** 절도 메인 세션이 검토한다.
- 라운드 2(clean review): 세 렌즈 전부를 다시 dispatch한다. 전체 계약을 다시 보되, 라운드 1 수정이 만든 구조 변화와 앞 라운드 보고의 미검토 항목을 명시적으로 대조한다. 구조적 `BLOCKER`·`MAJOR`가 0건이면 트랙을 마친다.
- 추가 라운드: 라운드 2 이후 새 구조적 `BLOCKER`·`MAJOR`가 구조 판정식을 통과한 경우에만 연다. 새 발견이 앞 라운드에서 왜 누락됐는지 그 라운드의 `PLAN-REVIEW-NN.md`에 적는다. 3라운드를 초과하면 자동 반복을 멈추고 남은 구조 결함과 반복 원인을 사용자에게 보고한다.
- 라운드가 끝날 때마다 `PLAN-REVIEW-NN`을 다음 번호로 append한다. `MINOR`는 근거와 함께 `pending-issues/`로 분리한다 — 등록 기준은 [`./issue-tracker.md`](./issue-tracker.md)를 따른다.
- 정지: 코드를 고치지 않는다. 커밋하지 않는다.

**구조 판정식.** subagent 발견을 게이트에 반영하기 전에 메인 세션이 순서대로 판정한다.

1. 이 발견이 DELTA의 범위·경계·의존·외부 계약을 바꾸는가?
2. 현재 DELTA 집합으로 이슈 완료 기준을 달성할 수 없는가?
3. 승인된 계약과 계획 결과가 직접 충돌하는가?

하나 이상 "예"면 구조적 발견이다 — 심각도를 판정한다. 전부 "아니오"면 구현 세부다 — 게이트에서 제외하고 해당 DELTA의 "트랙-4 확인사항" 절에 기록한다.

**트랙-2 심각도 적용 기준.** 공통 심각도 정의는 그대로 두고 트랙-2에서의 적용만 좁힌다.

- `BLOCKER` — 현재 DELTA 구조나 선행 조건으로 구현 자체가 불가능하다.
- `MAJOR` — 이슈 완료 기준을 어느 DELTA도 담당하지 않는다. 승인된 spec·ADR·아키텍처 불변식과 계획 결과가 직접 충돌한다. DELTA 경계나 실행 순서 때문에 완료 조건을 충족할 수 없다. DELTA가 크기 상한을 실제로 초과한다.
- `MINOR` 또는 트랙-4 확인사항 — 구현 helper·호출 순서·파일 배치 선택. 완료 조건이 이미 결과를 검증해 잘못된 구현이 RED로 잡히는 것. 계약 의미가 유지되는 문서 정밀도·유지보수성 문제. 상한 안의 예상 파일 수·diff 크기.

"구현자가 실수할 수 있음"만으로 `MAJOR`를 부여하지 않는다 — 구현 실수 가능성은 트랙-4와 트랙-6이 담당한다.

**리뷰 표면 통제.** 가이드가 없어서 현재 DELTA의 구현 선택이 열려 있는 `guide gap`만 게이트와 함께 다룬다. 현재 구현 선택을 막지 않는 일반화 과제는 `pending-guides/` 초안으로만 남기고 그 라운드의 추가 조사 대상으로 삼지 않는다 — 초안 작성 후 원래 DELTA의 구조 판정으로 즉시 돌아간다.

## 트랙-3. 테스트 계획과 최종 완료 체크리스트

- 입력: `01-계획.md`, `DELTA-*.md`, `PLAN-REVIEW-*.md`, DELTA가 연결한 개발 가이드
- 출력: `02-테스트-계획.md`, `03-최종-완료-체크리스트.md`
- 절차: `02-테스트-계획.md`는 적용 가이드의 테스트 층위·fixture·변이 규칙을 사용해 DELTA별 RED 시나리오, 회귀 대상, 실행 명령을 담는다. 테스트는 "트랙-4. DELTA 구현"의 세 분류(bug-catching RED / characterization / post-fix mutation)로 나눠 계획한다. `03-최종-완료-체크리스트.md`는 **트랙-5가 실측 증거와 대조할 항목 목록**이다. `01-계획.md`의 요구사항 추적표에서 파생한다 — 추적표의 각 행이 체크리스트 항목 하나 이상으로 연결돼야 한다. 각 항목은 판정 가능한 문장이어야 하고, 판정에 쓸 증거의 종류(테스트 제목, 명령 출력, 파일 경로)를 함께 적는다.
- 게이트: 체크리스트 항목에 연결되지 않은 추적표 행이 있으면 트랙-3을 완료하지 않는다.
- 정지: 코드를 고치지 않는다.

## 트랙-4. DELTA 구현

- 입력: 지정된 `DELTA-NN.md`, 그 DELTA가 연결한 가이드·함정, `02-테스트-계획.md`의 해당 DELTA 부분, `01-계획.md`의 의존 관계와 "## 결정"의 관련 Ruling
- 출력: 작업 브랜치 커밋, 실행 ledger(`progress.md`) 갱신
- 절차: subagent 협업 모드로 진행한다. DELTA마다 시작 시 세 가지를 판정해 ledger에 남긴다 — **구현 복잡도**(Micro·Standard·Risky), **검증 자동화**(Complete·Partial), **후속 기능적 의존**(None·Functional). 등급별 implementer와 실행 경로는 아래 "구현 복잡도"가, 독립 reviewer의 실행 시점은 "검증 자동화와 리뷰 시점"이 소유한다. 커밋은 메인 세션이 한다 — implementer 작업 하나가 끝날 때마다 diff를 확인하고 커밋한다.
- 게이트: **해당 DELTA의 완료 조건을 전부 충족한 경우에만 다음 DELTA를 시작한다.** 충족하지 못하면 정지하고 무엇이 미충족인지 보고한다.
- 검증: DELTA의 검증 명령(focused). `pnpm verify` 전량은 여기서 돌리지 않는다. focused 명령은 출력의 `Test Files`로 실제 선택 범위를 확인한다 — 패키지 `test` 스크립트는 경로가 고정돼 파일 인자가 필터로 겹쳐 전체를 실행할 수 있다. 파일 단위 실행은 `pnpm --filter <패키지> exec vitest run --root ../.. <테스트 파일...>` 형태를 쓴다.
- 재실행: 이미 완료한 DELTA를 사용자가 다시 지시하면 독립 reviewer 1회를 실행하고 발견을 수정한다.
- 정지: squash, `dev` 병합, push, GitHub 쓰기를 하지 않는다.

subagent 협업의 공통 규칙(파일 쓰는 subagent는 하나씩, worktree 격리 금지 등)은 "subagent 협업 규칙" 절을 따른다.

### 구현 복잡도

**Micro** — 다음을 모두 만족한다.

- 제품 소스 2파일 이하, 예상 제품 소스 diff 100줄 이하, 한 패키지 안에서 완료
- 새 외부 의존성·migration·보안 경계 변경 없음
- 공개 타입 변경이 없거나 승인된 내부 타입 변경뿐
- 설계 결정과 테스트 seam이 확정됐고 기존 패턴으로 구현 가능

실행: fast implementer → 메인 DELTA gate → 커밋.

**Standard** — 하나 이상 해당하고 Risky가 아니다.

- 제품 소스 3파일 이상, 복수 소비처 통합, 기존 패턴 안에서 구현 판단 필요
- 승인된 공개 동작 변경, spec과 코드 동시 갱신

실행: standard implementer → 메인 DELTA gate → 커밋 → 리뷰 시점 판정.

**Risky** — 하나 이상 해당한다.

- 패키지 경계 또는 공개 API shape 변경, 신규 외부 의존성
- DB migration·production config·credential·보안 경계 변경
- 서로 다른 패키지 3개 이상, DELTA 크기 상한 근접·초과
- 구현 중 새 설계 결정 발생, rollback 비용 높음

실행: implementer와 spec review·code-quality review를 분리한 prompt 세트 또는 별도 사용자 판단. 트랙-5·6과 중복되는 검토를 시작 전에 명시한다.

**implementer 정의.** fast implementer는 저비용 모델의 파일 쓰기 subagent 하나, standard implementer는 세션 기본 모델의 파일 쓰기 subagent 하나다. 모델을 지정할 수 없는 환경이면 둘 다 기본 모델을 쓴다. 둘 다 아래 구현 prompt만 입력으로 받고, 상태·변경 파일·검증·우려만 짧게 보고한다 — 별도 장문 보고서 파일을 만들지 않는다.

**등급 상승.** 구현 중 현재 등급 조건을 벗어나면 변경을 보존하고 정지한다. 메인 세션이 새 등급으로 절차를 전환하고 전환 사실을 ledger에 남긴다. 제품 범위·공개 계약 결정이 새로 필요할 때만 사용자에게 묻는다.

### 검증 자동화와 리뷰 시점

**Complete** — 다음을 모두 만족한다: 각 사용자 관찰 가능 완료 조건을 테스트가 판정한다. 정적 조건에 재현 가능한 명령이 있다. RED 또는 mutation이 잘못된 구현을 검출한다. focused package gate가 있다. **Partial** — 하나라도 해당한다: 수동 판정 필요, 테스트 seam 부재, 완료 조건 일부가 문서 해석에 의존, 외부 환경·브라우저·성능 측정 필요, 구현 중 예상 밖 실패가 발생하고 원인이 완전히 해소되지 않음.

독립 reviewer는 등급만으로 자동 실행하지 않는다.

**즉시 reviewer** — 하나 이상 해당하면 커밋 후 바로 실행한다.

- Risky DELTA, 검증 자동화 Partial, 후속 DELTA가 현재 결과에 기능적으로 의존
- implementer가 우려를 반환, 계획과 다른 구현 선택 발생, RED가 예상과 다른 원인으로 실패
- diff가 계획 파일 범위를 벗어나거나 제품 소스 200줄을 초과

**트랙-5·6으로 이연** — 다음을 모두 만족하면 per-DELTA 리뷰를 생략하고 트랙-5·6의 독립 리뷰가 담당한다: Micro 또는 Standard, 검증 자동화 Complete, 후속 기능적 의존 None, implementer 우려 없음, 계획 범위 안 구현, 메인 DELTA gate 통과. 단순 diff 충돌 회피 순서는 기능적 의존이 아니다. 마지막 DELTA는 기본적으로 이연 후보다. 트랙-5·6을 바로 이어 실행하지 않아도 이연할 수 있다 — 트랙-8의 게이트(`IMPL-REVIEW-*.md` 없이 병합 금지)가 리뷰 없는 병합을 막는다.

### 검증 책임

같은 완료 조건을 여러 주체가 반복 판정하지 않는다.

- implementer — bug-catching RED를 실행하고(characterization은 구현 전 통과 여부를 기록), 구현하고, 같은 파일 집합의 targeted GREEN을 실행한다.
- 메인 세션 — diff와 DELTA 범위를 대조하고, DELTA 검증 명령 전체를 한 번 실행하고, 정적 완료 조건을 확인하고, 리뷰 시점을 판정하고, gate 통과 후 커밋한다.
- reviewer — 기존 최신 증거를 입력으로 받고 재생산하지 않는다. 누락·과잉·결함만 보고하고, 완료 조건을 다시 서술하거나 테스트 결과를 복제하지 않는다. 발견을 재현할 때만 명령을 실행한다. 발견이 없으면 판정·심각도별 0건·확인 범위만 5줄 이하로 남긴다.

테스트는 세 종류를 구분해 계획하고 보고한다 — **bug-catching RED**(기존 결함에서 반드시 실패한다), **characterization**(기존 동작·비목표 회귀를 고정한다. 구현 전 통과할 수 있다), **post-fix mutation**(구현 후 잘못된 변이를 잡는다. 기존 코드에서 실패할 필요는 없다). 신규 테스트 수를 RED 수로 보고하지 않는다.

### 실행 ledger와 구현 prompt

트랙-4 상세 증거는 작업당 `progress.md` 하나가 소유한다. DELTA마다 등급 판정(복잡도·자동화·후속 의존·리뷰 시점), agent 호출 수, 테스트 분류별 결과, 전체 gate 결과, 변경 파일 수, 남은 위험을 기록한다. Git diff를 별도 파일로 복제하지 않고(`review-DELTA-NN.diff` 금지 — Git이 diff를 소유한다), implementer 장문 보고서를 만들지 않는다. 시간은 성과 gate가 아니라 병목 관찰값이다.

효율 목표: implementer 호출 1, reviewer 호출 조건부 0~1, 전체 DELTA gate 1회, diff 복제 파일 0, DELTA당 ledger 30~40줄 이하. reviewer가 발견 0건·수정 0건인 실행이 반복되면 즉시 reviewer 조건을 좁히고, reviewer가 트랙-5·6보다 먼저 결함을 반복 검출하면 조건을 넓힌다.

메인 세션은 다음 prompt의 꺾쇠 항목만 실제 값으로 채워 implementer에게 전달한다. 다른 DELTA의 테스트 계획과 최종 체크리스트를 전달하지 않고, DELTA 내용을 별도 task brief 파일로 복제하지 않고, implementer가 작업 폴더 전체를 탐색하게 하지 않는다.

```text
<DELTA 경로>를 구현한다.

입력:
- 목적: <DELTA 목적>
- 변경 대상: <허용 파일과 책임>
- 완료 조건: <조건과 각 조건의 검출 변이>
- 테스트: <해당 DELTA의 분류별 테스트와 focused 명령>
- 적용 계약: <가이드·함정·관련 Ruling>
- 선행 변경: <현재 코드에 이미 반영된 선행 DELTA 결과>
- 트랙-4 확인사항: <있으면 기재>

실행:
1. 현재 코드와 테스트로 DELTA 전제가 성립하는지 확인한다.
2. bug-catching RED를 먼저 재현하고 characterization의 현재 결과를 기록한다.
3. 최소 구현으로 GREEN을 만들고 targeted 검증을 실행한다.
4. 허용 파일 밖 변경, 계획과 다른 구현 선택 또는 새 사용자 결정이 필요하면 멈추고 보고한다.
5. merge, push, GitHub 쓰기, 재그룹화와 커밋은 수행하지 않는다.

반환: 상태, 변경 파일과 diff 요약, RED/GREEN 증거, 실행한 명령과 결과, 계획과 달랐던 사실, 우려와 범위 밖 발견.
```

## 트랙-5. 누락 탐지

- 입력: `03-최종-완료-체크리스트.md`, 작업 브랜치의 실측 증거
- 출력: 체크된 `03-최종-완료-체크리스트.md`, `IMPL-REVIEW-NN.md`
- 렌즈: **계획 대비 누락만 본다.** 체크리스트의 각 항목을 실측 증거와 대조해 `PASS` / `FAIL` / `BLOCKED` / `NOT_RUN`으로 판정한다. 코드 품질은 보지 않는다 — 그건 트랙-6이다.
- 검증: 진입 시 `pnpm verify` 전량 1회. 재실행할 때도 다시 실행한다.
- 절차: `FAIL` 항목을 수정하고 같은 범위를 다시 판정한다. 판정 근거는 재현 가능한 증거로 남긴다 — 테스트 제목, 명령과 출력, 파일 경로와 줄 번호.
- 정지: 재그룹화, `dev` 병합, push, GitHub 쓰기를 하지 않는다. 재그룹화는 트랙-8의 전유 행위다. 수정 커밋은 작업 브랜치에 세분화된 채로 쌓는다.

## 트랙-6. 결함 탐지

- 입력: `git diff dev...<작업 브랜치>`, 대상 코드, 관련 개발 가이드, 적용 조건이 맞는 `ACTIVE` pitfall, `AGENTS.md`의 아키텍처 불변식
- 출력: `IMPL-REVIEW-NN.md`(트랙-5와 같은 연속 시퀀스)
- 렌즈: **계획 문서를 읽지 않는다.** DELTA 경계에서 생긴 횡단 결함, 회귀, 불변식 위반, 계획이 애초에 놓친 것을 찾는다. 계획을 읽으면 계획의 사각지대를 그대로 물려받는다 — 그것을 막는 것이 이 트랙의 목적이다.
- 리뷰 강도: 진입 시 변경 전체의 위험으로 reviewer 수를 정한다. 판정 신호는 트랙-4의 등급·검증 자동화 판정을 재사용한다 — 별도 등급 체계를 만들지 않는다.
  - **Light(1개)** — 단일 패키지 내부 변경이고 검증 자동화 Complete이고 위험 신호가 없다. 렌즈: 정확성·회귀·경계 통합.
  - **Focused(2개)** — 복수 소비처 또는 DELTA 경계 상호작용이 있거나, 승인된 공개 동작 변경이 있다. 렌즈: 정확성·불변식 / DELTA 경계·테스트 갭.
  - **Full(3개)** — 저장 형식·보안·공개 계약을 바꾸거나, 여러 패키지를 횡단하거나, 검증 자동화 Partial이다. 렌즈: 정확성 / 회귀·불변식 / DELTA 경계·테스트 갭.
- 절차: 읽기 전용 subagent에 병렬 dispatch한다. reviewer는 파일·줄 근거와 최소 재현(입력, 실제/기대 결과)을 제출하고, 주장 확인에 필요한 최소 명령만 직접 실행한다. 메인 세션이 보고를 합쳐 중복을 제거하고 진짜 결함인지 직접 확인한다.
- 수정 소유자: 진짜 결함으로 확인한 뒤 수정 크기를 판정한다. **Micro 수정**(단일 패키지, 국소 수정, 새 설계 판단 없음, focused test로 완전 검증 가능)은 메인 세션이 직접 RED/GREEN과 focused gate를 수행한다 — 이 크기에서는 handoff 비용이 구현 비용보다 크다. 그 외는 파일 쓰기 subagent에 하나씩 순차 위임하고 메인 세션이 diff와 focused gate를 확인해 커밋한다.
- 수정 규칙: 회귀 테스트를 먼저 추가해 RED를 확인한 뒤 GREEN 구현을 한다. 기존 테스트를 지우거나 assertion을 약화해 통과시키지 않는다. 회귀 테스트가 같은 입력과 기대값을 고정하면 수정 후 같은 내용을 ad-hoc 스크립트로 다시 증명하지 않는다 — 테스트가 표현하지 못하는 경계만 별도 실행한다.
- 정지: 재그룹화, `dev` 병합, push, GitHub 쓰기를 하지 않는다. 재그룹화는 트랙-8의 전유 행위다. 수정 커밋은 작업 브랜치에 세분화된 채로 쌓는다.

## 트랙-7. 작업 결과

- 입력: 작업 폴더 전체
- 출력: `04-작업결과.md`, 대상 이슈별 완료 댓글 초안(`pending-issues/NN.md`, [`./issue-tracker.md`](./issue-tracker.md)의 "초안 형식" — `종류: 댓글`)
- 형식: `AGENTS.md`의 "완료 보고"를 따른다.
- 절차: `git log --oneline dev..<작업 브랜치>`와 `git diff --stat dev..<작업 브랜치>`로 실제 변경을 대조한다. 보고가 주장하는 범위가 실측과 다르면 실측을 따르고 차이를 보고에 적는다. `04-작업결과.md`가 확정한 내용을 근거로 대상 이슈마다 완료 댓글 초안을 쓴다 — 이미 같은 이슈를 대상으로 하는 `상태: 미등록` 댓글 초안이 있으면 그 파일을 덮어쓰고 새 번호를 만들지 않는다([`./issue-tracker.md`](./issue-tracker.md)의 "완료 댓글과 완료 보고" 표를 따른다). 트랙-8은 이 초안을 게시만 한다 — 새로 작성하지 않는다.
- 정지: 커밋 해시를 쓰지 않는다. 이 시점의 해시는 트랙-8의 재그룹화로 사라진다. 참조 방식은 "커밋 해시 참조" 절을 따른다.

## 트랙-8. 병합과 등록

트랙-8 실행 지시는 작업 브랜치의 `dev` fast-forward merge를 허가한다. push·tag·PR 생성과 `dev` → `main` 병합은 포함하지 않는다. GitHub 게시·종료는 [`./issue-tracker.md`](./issue-tracker.md)를 따른다.

- 입력: `04-작업결과.md`, `IMPL-REVIEW-*.md` 최소 하나, `pending-issues/*`, `pending-guides/*`, `pending-pitfalls/*`
- 출력: `dev`의 커밋, GitHub 이슈·댓글, `docs/history/<yyyyMMdd>-<NN>-<제목>.md`, `_meta.md`의 `상태: 완료`
- 게이트: **리뷰 트랙을 거치지 않은 구현은 `dev`에 병합하지 않는다.** `IMPL-REVIEW-*.md`가 하나도 없으면 아무것도 바꾸지 않고 정지하고 무엇이 없는지 보고한다. 사용자가 그 실행에서 리뷰 생략을 명시 지시한 경우에만 예외로 하고, 생략한 사실과 지시 내용을 `04-작업결과.md`와 `docs/history/`의 이력에 적는다.
- 절차: 메인 세션이 단독으로 직렬 수행한다. subagent에 위임하지 않는다 — 상태 파일과 git 이력을 한 세션이 다뤄야 한다.
  1. `pnpm verify` 전량을 통과시킨다.
  2. 작업 브랜치 커밋을 "재그룹화 실행 명령" 절에 따라 의미 단위로 재그룹화한다.
  3. `git switch dev` 후 `git merge --ff-only <작업 브랜치>`. ff가 거절되면 현재 `dev` 기준으로 2단계를 다시 실행한다.
  4. `git branch -d <작업 브랜치>`로 삭제하고 백업 ref를 정리한다.
  5. `_meta.md`의 `상태`를 `완료`로 바꾼다. 확정 해시는 9단계의 이력이 기록한다.
  6. [`./issue-tracker.md`](./issue-tracker.md)에 따라 GitHub 게시·종료를 판단하고 사용자 확인 없이 수행한다.
  7. 닫지 않은 이슈는 미충족 기준과 다음 조치를 완료 댓글이나 보고에 남긴다.
  8. 가이드 정비를 검토한다 — 이번 작업에서 드러난 기존 가이드의 모호하거나 빠진 문구를 수정·보강하고, `pending-guides/*`와 `pending-pitfalls/*`의 승격을 판단해 등록한다. 수정·등록하면 해당 INDEX를 같은 변경에서 동기화하고, 무엇을 왜 바꿨는지 9단계의 이력에 남긴다.
  9. `docs/history/<yyyyMMdd>-<NN>-<제목>.md`를 쓴다.
- 보고: 삭제한 브랜치명, 미푸시 커밋 수, 닫은 이슈 번호를 남긴다.
- 정지: `dev`를 push하지 않고 `dev` → `main` 병합도 하지 않는다. 둘 다 사용자가 직접 지시하거나 수행한다.

## DELTA 계약

### `DELTA-NN.md` 형식

필수 섹션은 여덟이다. 트랙-1이 쓰고 트랙-2가 적용 누락과 충돌을 검토한다.

1. **목적** — 한 문장.
2. **배경** — 왜 이 순서인가. 선행 DELTA 의존이 있으면 명시한다. 앞선 맥락이 없는 에이전트가 이 절만 읽고 왜 지금 이것을 하는지 알 수 있어야 한다.
3. **변경 대상** — 예상 파일 경로 목록.
4. **완료 조건** — 검증 가능한 문장 목록. 각 조건마다 **그 조건을 지게 만드는 변이**를 함께 적는다.
5. **검증 명령** — 복사해 바로 붙여 넣을 수 있는 형태.
6. **범위 밖** — 이 DELTA에서 하지 않을 것.
7. **적용 계약과 가이드** — 관련 spec·ADR, `G-<카테고리>-<번호>` 가이드와 기존 helper·pattern. 해당 없음도 명시한다.
8. **적용 함정** — [`docs/pitfalls/INDEX.md`](../pitfalls/INDEX.md)의 `ACTIVE` 항목 중 적용 조건이 이 DELTA와 맞는 항목과 적용 지점. 없으면 "적용 함정 없음"을 명시한다.

선택 섹션 하나를 더 둘 수 있다.

9. **트랙-4 확인사항**(선택) — 트랙-2가 구조 판정식으로 게이트에서 제외한 구현 세부 발견. 구현자가 이 DELTA 파일만 읽고도 확인할 수 있게 여기에 둔다 — `PLAN-REVIEW-NN.md`에만 남기지 않는다.

완료 조건에 변이를 적지 못하면 그 조건은 검증 불가하다는 뜻이고, 검증 불가한 조건만 있는 DELTA는 성립하지 않는다. 그런 DELTA는 앞뒤에 합친다.

### 크기 규칙

기준은 **리뷰어가 이 DELTA를 판정하는 동안 컨텍스트가 가득 차지 않는 것**이다. 리뷰어가 담아야 하는 것은 `DELTA 문서 + 변경 diff + 변경 파일 전문 + 직접 의존 파일`이다. 그중 계획 시점(트랙-1)에 예측할 수 있는 것을 상한으로 쓴다.

상한 — 하나라도 넘으면 나눈다.

- 변경 diff 700줄(추가 + 삭제)
- 신규·수정 소스 파일 6개
- 리뷰어가 전문을 읽어야 하는 파일 합계 2,000줄

하한 — 만족하지 못하면 앞뒤 DELTA에 합친다.

- 완료 조건이 1개 이상이고, 그것을 RED로 만들 변이를 적을 수 있다.

분할 신호 — 상한 안이어도 나누는 편이 낫다.

- 완료 조건 한 문장에 "그리고"가 두 번 이상 나온다.
- 서로 무관한 공개 계약 두 개를 동시에 바꾼다.
- 서로 다른 패키지 세 개 이상을 건드린다.

**실측 보정.** 위 수치는 첫 기준선이다. 트랙-4에서 리뷰 subagent가 파일을 다 읽지 못했다고 보고하거나 컨텍스트 압박으로 판정을 유보하면 DELTA를 쪼개고, 정상 분할 지식은 `pending-guides/`에 남긴다. 가이드를 따르지 않았거나 모호하게 해석해 반복된 실수만 `pending-pitfalls/`에 남긴다.

## 리뷰 산출물

`PLAN-REVIEW-NN.md`와 `IMPL-REVIEW-NN.md`는 append-only 시퀀스다. 이전 회차를 덮어쓰지 않는다.

`IMPL-REVIEW-NN.md`는 **트랙-5와 트랙-6이 공유하는 하나의 연속 시퀀스**다. 트랙-5가 `01`을 쓰면 트랙-6은 `02`를 쓴다. 재실행도 같은 시퀀스에 이어 붙인다. 파일 머리말이 어느 트랙의 어떤 초점인지 밝힌다.

형식 — 네 절만 가진다.

```markdown
# IMPL-REVIEW-01

- 트랙: 5 (누락 탐지)
- 초점: <초점>
- 대상: <작업 브랜치> / DELTA-01 ~ DELTA-04
- 시점: yyyy-MM-dd

## 발견                      <!-- 확정 결함만 기록한다 -->

### F1 <제목> — MAJOR

- 위치: <파일:줄>
- 재현: <명령 또는 조건>
- 실제/기대: <실측>
- 위반 계약: <문서 경로와 문구>

## 처리                      <!-- 발견별 수정 / 범위 밖 / 오탐과 변경한 테스트·코드 -->

## 검증                      <!-- 최종 focused gate와 결과 -->

## 남은 위험                 <!-- 현재 변경으로 닫히지 않은 위험만 -->
```

기록하지 않는 것: 어느 reviewer가 같은 결함을 몇 번 발견했는지, 조사 중 확인한 모든 정상 경로, 테스트 전체 출력, commit message와 중복되는 변경 설명.

`## 남은 위험`을 비워두지 않는다. 없다고 판단했으면 어디를 확인해서 그렇게 판단했는지 적는다.

심각도는 [`../process/development-lifecycle.md`](../process/development-lifecycle.md)의 `BLOCKER` / `MAJOR` / `MINOR`를 그대로 쓴다. **`BLOCKER`·`MAJOR`는 위반한 필수 요구사항·회귀 계약의 문서 경로와 문구를 인용할 때만 부여한다.** 명시 계약 없이 품질 저하만 확인했으면 `MINOR`로 판정하거나 계약 공백으로 보고한다. `BLOCKER`와 `MAJOR`는 수정하고 같은 범위를 다시 검증한다. 수정하지 않는 `MINOR`는 근거와 함께 `pending-issues/`로 분리한다. 분리 대상은 [`./issue-tracker.md`](./issue-tracker.md)의 "등록 기준"을 통과하는 것뿐이다.

## 검증 게이트

| 시점             | 검증                       |
| ---------------- | -------------------------- |
| 트랙-4 각 DELTA  | DELTA의 검증 명령(focused) |
| 트랙-5 진입      | `pnpm verify` 전량 1회     |
| 트랙-8 병합 직전 | `pnpm verify` 전량 1회     |

실패가 있으면 baseline 실패와 현재 변경이 만든 실패를 구분하고 성공으로 보고하지 않는다.

## 브랜치 수명과 커밋

1. 트랙-0에서 `dev`에서 분기해 작업 브랜치를 만든다. worktree는 만들지 않는다.
2. 트랙-4·5·6이 같은 브랜치에 세분화된 커밋을 그대로 누적한다.
3. 트랙-8이 `pnpm verify` 전량 통과 후 의미 단위로 재그룹화하고 `dev`로 ff-only 이전한다.
4. 이전 후 브랜치를 삭제하고 백업 ref를 정리한다.
5. 작업 브랜치는 push하지 않는다. push 대상은 `dev`뿐이고 명시적 지시를 기다린다.

작업 브랜치는 작업당 하나이고 여러 개가 동시에 존재할 수 있다. 각각 `dev`에서 분기한다. 앞 작업의 산출물이 필요한 의존 작업일 때만 그 브랜치에서 분기하고 의존을 실행 ledger(`progress.md`)에 적는다.

### 커밋 해시 참조

해시는 작업 브랜치가 `dev`로 이전되는 순간에만 불변이 된다. 이전 전에는 이슈, 댓글, 초안과 어느 산출물에도 해시를 쓰지 않는다. 참조는 작업 브랜치명, 파일 경로와 줄 번호, 테스트 제목, 검증 명령 출력으로 한다. 이전 후 확정된 해시는 트랙-8이 쓰는 `docs/history/` 이력이 기록한다 — `_meta.md`에는 쓰지 않는다.

## 재그룹화 실행 명령

이 절이 실행 명령, 그룹 순서와 무결성 판정을 함께 소유한다.

### 전제

다음이 어긋나면 아무것도 바꾸지 않고 정지한다.

- `git status --short`가 비어 있어야 한다.
- 작업 브랜치가 존재하고 `git log --oneline dev..<브랜치>`가 비어 있지 않아야 한다.
- 이전 실행이 남긴 `-tip` ref가 없어야 한다. `git for-each-ref refs/backup/<브랜치>-tip`이 빈 출력이어야 한다.

더러운 작업 트리에서 재조립을 시작하면 미커밋 변경이 그룹 커밋에 조용히 접혀 4단계의 트리 diff가 비지 않는다. 그 상태로 "되돌리고 2단계부터 다시 한다"를 반복해도 원인이 트리 오염이면 끝나지 않는다 — 재조립을 시작하기 전에 이 전제부터 확인한다.

`-tip`이 남아 있으면 더 조용히 깨진다. 5단계를 건너뛰어도 6단계의 `git branch -f`가 실패하지 않고 **이전 실행의 커밋**을 브랜치에 박는다. 그 트리는 `-pre-squash`와 같으므로 6단계 재대조가 빈 출력으로 통과하고 `git merge --ff-only`도 성공한다 — 이번 실행의 그룹 분할과 커밋 메시지만 사라지고 아무 게이트도 울리지 않는다. `-tip`이 남아 있다는 것은 이전 실행이 6단계나 7단계에서 끝나지 않았다는 뜻이다. 그 실행을 먼저 정리한다.

### 절차

1. 백업 ref를 남긴다. 백업 없이 재조립하지 않는다.

   ```bash
   git update-ref refs/backup/<브랜치>-pre-squash HEAD
   ```

2. 그룹을 정한다. `git log --oneline --name-only dev..HEAD`로 같은 파일·같은 줄을 왕복하는 상쇄 쌍을 먼저 찾는다. revert·되돌림 성격의 커밋은 원인 커밋과 같은 그룹에, 원인 커밋 뒤에 둔다.
3. `dev`에서 분리해 그룹별로 재조립한다. 커밋을 원래 순서대로 나열하고 그룹마다 한 번 커밋한다.

   ```bash
   git switch --detach dev
   git cherry-pick -n <그룹1 커밋...>
   git commit -m "<그룹1 메시지>"
   git cherry-pick -n <그룹2 커밋...>
   git commit -m "<그룹2 메시지>"
   ```

   커밋 메시지는 한글로 쓰고 `Co-Authored-By`와 생성 표시 라인을 넣지 않는다.

   `git commit`이 `커밋할 사항 없음`으로 실패하면 그 그룹은 내부에서 전부 상쇄된 것이다. 에러가 아니므로 그룹을 버리고 다음으로 넘어가되, 커밋을 의도적으로 버렸다는 사실을 보고에 적는다.

   `git cherry-pick`이 충돌로 멈추면 `git cherry-pick --continue`를 쓰지 않는다. `-n`이 남긴 스테이지 변경 때문에 `로컬 변경 사항을 cherry-pick 때문에 덮어 쓰게 됩니다`로 실패한다(exit `128`). 해결 경로는 다음이다.

   ```bash
   # 충돌 해결 후
   git add <파일>
   git cherry-pick --quit          # 시퀀서 상태만 정리한다. 작업 트리는 그대로 남는다
   git cherry-pick -n <남은 커밋>  # 나머지를 이어서 pick
   ```

4. 트리를 대조한다. 3단계에서 의도적으로 버린 그룹이 없다면 빈 출력이어야 한다. 버린 그룹이 없는데도 비어 있지 않으면 그룹 순서가 잘못된 것이다. 되돌리고 2단계부터 다시 한다.

   ```bash
   git diff refs/backup/<브랜치>-pre-squash HEAD --stat
   ```

5. 그룹 경계마다 typecheck가 통과하는지 확인한다. 검증을 시작하기 전에 재조립 tip을 ref로 고정한다 — 이 단계가 HEAD를 중간 그룹 커밋으로 옮기므로, 고정해 두지 않으면 6단계가 그 HEAD를 브랜치에 박아 뒤 그룹을 조용히 버린다.

   ```bash
   git update-ref refs/backup/<브랜치>-tip HEAD   # 재조립 tip 고정. 검증 전에 한다
   git switch --detach <그룹 커밋>                # 그룹마다 반복
   # 해당 범위의 focused 검증을 실행한다
   ```

   역순으로 검증하거나 일부만 검증하거나 중간에 멈춰도 tip은 ref에 남는다.

6. 작업 브랜치를 재조립 tip으로 옮기고 `dev`로 이전한다. `HEAD`를 대상으로 쓰지 않는다 — 5단계가 HEAD를 중간 그룹 커밋에 남겨 뒀으면 뒤 그룹이 사라지고, 그래도 `merge --ff-only`는 fast-forward라 성공한다.

   ```bash
   git branch -f <브랜치> refs/backup/<브랜치>-tip
   git switch <브랜치>
   git diff refs/backup/<브랜치>-pre-squash <브랜치> --stat   # 병합 직전 재대조. 4단계와 같은 기대치다
   git switch dev
   git merge --ff-only <브랜치>
   ```

   재대조가 4단계와 같은 결과가 아니면 병합하지 않는다. 5단계가 HEAD를 옮긴 뒤 브랜치가 tip이 아닌 커밋을 가리키게 됐다는 뜻이다.

   ff가 거절되면 재조립 중 `dev`가 움직인 것이다. 3단계를 현재 `dev` 기준으로 다시 실행한다.

7. `git branch -d <브랜치>`로 삭제하고 ref를 정리한다. 백업 ref는 6단계의 재대조와 병합이 끝난 뒤에만 지운다.

   ```bash
   git update-ref -d refs/backup/<브랜치>-tip
   git update-ref -d refs/backup/<브랜치>-pre-squash
   ```

### 금지

- `git rebase -i`. 에이전트 세션은 `GIT_EDITOR=true`라 아무것도 합치지 않은 채 `Successfully rebased`와 exit code `0`을 낸다 — [`PIT-0023`](../pitfalls/PIT-0023-editor-opening-git-commands-succeed-silently.md). `GIT_SEQUENCE_EDITOR` 우회도 쓰지 않는다.
- 명령의 성공 문구를 결과 판정 근거로 쓰기. 판정은 4단계와 6단계의 트리 diff로만 한다. `merge --ff-only`의 성공은 뒤 그룹이 사라져도 나온다.
- push, tag, PR 생성. `dev` push는 사용자가 별도로 지시한다.
- `main`을 대상으로 하는 merge, rebase, push.
- `git reset --hard`, 강제 push, 광범위한 `git clean`.

## pending-issues, pending-guides와 pending-pitfalls

셋 다 **어느 트랙에서든 언제라도 추가할 수 있다.** 현재 범위 밖에서 발견한 것을 현재 변경에 섞지 않기 위한 자리다.

**예외 — 이전 전 hash.** 작업 branch commit hash가 이전 전 산출물에 남은 경우 현재 트랙·DELTA 범위와 무관하게 즉시 수정한다. pending 항목으로 미루지 않는다. 위 "커밋 해시 참조" 절이 원본이다. 위반을 서술할 때도 hash 값은 인용하지 않고 수정 산출물을 포함해 다시 검사한다.

`pending-issues/NN.md` — 등록 전 이슈·댓글 초안. 발견 위치, 영향, 현재 범위에서 제외한 이유, 완료 조건을 적는다. 파일 형식, 등록 기준과 게시 승인은 [`./issue-tracker.md`](./issue-tracker.md)가 소유한다 — 초안은 그 문서의 "초안 형식"을 그대로 따른다.

`pending-guides/NN.md` — 신규 가이드 또는 기존 가이드 수정·보강 초안. 적용 조건 / 구현 규칙 / 완료 기준 / 관련 기존 helper를 적는다. 기존 가이드 보강이면 대상 `G-<카테고리>-<번호>`와 모호했던 문구를 함께 적는다.

`pending-pitfalls/NN.md` — 가이드나 명시적 계약을 따르지 않았거나 모호하게 해석해 반복된 실수. 적용 조건 / 오해하기 쉬운 신호 / 원인 / 탐지를 적는다. 발견한 정상 회피 경로는 `pending-guides/` 초안에 적는다. 승격 기준은 [`../pitfalls/INDEX.md`](../pitfalls/INDEX.md)의 "승격 기준"이 소유한다.

## docs/history

`docs/history/<yyyyMMdd>-<NN>-<제목>.md`. `04-작업결과.md`의 압축본이다. `NN`은 작업 폴더 이름의 `NN`과 같은 그날 순번이다. `_works/`는 gitignore 대상이라 저장소에 남지 않으므로, 남길 값이 있는 것만 여기로 옮긴다.

파일에 담는 것과 담지 않는 것, 보관 정책은 [`../history/README.md`](../history/README.md)가 소유한다. 여기에 복제하지 않는다. 에이전트는 이 디렉터리의 파일을 삭제하지 않는다.

## subagent 협업 규칙

트랙-0, 트랙-2, 트랙-4, 트랙-6이 이 모드로 실행한다(트랙-0은 사전 조사가 여러 갈래로 갈릴 때만 조건부로 쓴다). 메인 세션은 조율자이고 조사·구현·리뷰는 subagent가 한다 — 예외는 트랙-6의 Micro 수정 하나뿐이고 그 조건은 트랙-6 절이 소유한다. 트랙-1·3·5·7(문서 작성과 판정)은 산출물을 한 세션이 직접 쓰므로 이 모드를 쓰지 않는다. 트랙-8(병합과 등록)도 이 모드를 쓰지 않는다 — 상태 파일과 git 이력을 한 세션이 직렬로 다뤄야 한다.

쓰는 이유는 둘이다. 조사와 리뷰를 여러 시선으로 나눠 파일 단위 시야에 갇히는 것을 줄인다. 메인 세션의 컨텍스트를 조율과 판단에 남긴다.

- subagent는 이 세션의 맥락을 물려받지 않는다. 프롬프트에 대상 이슈 번호, 작업 브랜치명, 작업 폴더 경로, 읽어야 할 문서 경로, 편집 허용 범위와 반환 형식을 모두 적는다.
- subagent에 worktree 격리를 주지 않는다. 작업 트리 하나를 공유하므로 **파일을 쓰는 subagent는 한 번에 하나만 띄운다.** 병렬 dispatch는 읽기 전용 조사·리뷰에만 쓴다.
- 커밋은 메인 세션이 한다. subagent 작업 하나가 끝날 때마다 diff를 확인하고 커밋한다. 커밋 단위와 메시지는 재그룹화 대상이라 한 곳에서 정한다.
- 정지 조건은 subagent에도 그대로 적용된다. push, GitHub 쓰기, `dev` 병합과 재그룹화 금지를 프롬프트에 명시한다.
- subagent 보고는 근거와 함께 받는다 — 파일 경로와 줄 번호, 테스트 제목, 실행한 명령과 출력. 근거 없는 "고쳤다"는 받아들이지 않고 메인 세션이 직접 확인한다.
- 사용자 결정이 필요한 지점은 subagent가 추측하지 않고 그대로 올린다. 사용자에게 묻는 것은 메인 세션이다.
